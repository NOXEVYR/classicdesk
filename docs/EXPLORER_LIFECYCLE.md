# Explorer 布局修复与窗口重建

当前状态（2026-10-25）：私有 v17 已通过原版设置面板的真实 Modern → Ribbon 重建及拖动、顶部点击、地址栏、视频上下文、折叠/展开、最小化恢复和关闭重开验证；同次开机自动加载另由实机日志和用户确认。范围和局限见 [验收记录](RELIABILITY_ACCEPTANCE.md)。以下带日期段落保留当时结论，不表示当前仍停在该阶段。

## 2026-10-19：关闭后确认与后台回归（私有 v16）

v15 已完成整套隔离检查，但实际重建尚未通过。继续查到关闭后确认仍会在首次暂时性 COM/UIA 读取失败或清单不完整时立即退出，与打开后的有界等待不一致。v16 在原期限内仅重读清单；原窗口关闭请求仍然最多一次。桌面身份变化立即停止，非暂时错误不重试；发送关闭前显式检查取消与期限。

新增用同一测试源码引用冻结 v15 程序集的对照，18 项中 4 项失败；修正后 18 项全部通过。失败用例覆盖暂时性读取、持续失败、取消和过期请求边界。核心流程 31 项、窗口诊断 33 项也通过。它们均不发送真实输入、不打开或关闭文件窗口，不代表 COM Quit 实机成功。此前 v15 的完整回归保留；v16 只重跑受影响检查，不把旧完整检查改写为 v16 全量结果。

用户要求在工作期间继续后台修复，因此此阶段不做鼠标键盘自动化、不启动交互窗口、不切换服务或重启。下次实际验收可以由用户在重建面板主动操作，后台读取结果；拖动和顶部点击由用户完成，避免争抢输入设备。

## 2026-10-19：真实重建未通过及私有 v15

v14 实机重建发出了单次打开请求，替代窗口已出现。该窗口的标题拖动、主页／共享／查看和地址栏点击实际通过，收起功能区后导航栏可见。但辅助程序随后异常退出，原窗口仍保留；完整重建未通过。此前错误被统一替换为通用 IOException，不能从该结果反推具体失败的 COM 调用。

v15 的失败返回增加动作、受限阶段名、异常类型及 HRESULT，不包含目录、窗口标题或异常原始消息。新窗口创建后的只读观察对明确的暂时性 COM/UIA 错误、尚未注册的 Document/Folder/Selection 和暂时不完整的清单，在原截止时间内重新读取；程序错误、访问拒绝、身份变化和多窗口歧义仍停止。打开和关闭请求始终最多各一次，未知结果不重试。新增隔离检查覆盖短暂失败后恢复、持续失败超时、非暂时错误、打开失败和身份变化。

辅助程序提供 `validate-close` 只读分支，执行相同的双次身份/修订检查及保留 COM 对象的 HWND 读取，在 Quit 前返回。实机只读验证通过说明关闭前的 COM 对象仍可读取，不证明 Quit 成功，也不证明先前失败由初始化时序引起。实际完整重建、首个新进程窗口与增强冷启动仍待验证。

## 2026-10-19：旧窗口标签读取修正（私有 v14）

现场 WinUI 标签同时暴露可见控件 peer 和逻辑 item peer，两者的 RuntimeId 不同；可见且已选中的标签也支持 VirtualizedItem。此前把支持该接口直接视为“未实现”，以及假定选中项必须等于树节点，都会让实际单标签窗口的 TabCount 变成未知。

现在先核对唯一 TabView 和它的 TabListView，读取标签自身声明的 SelectionContainer，再核对两个 peer 的父列表、选择容器、可见性和实际矩形。通过 ItemContainer 的逻辑枚举确认只有一个项目（最多读取两个）；第二个项目无论可见与否都拒绝重建。枚举不调用 Realize、Select 或 Scroll。读完重查可见项目、选择和逻辑项目，修订号同时覆盖两种 peer 身份。没有逻辑枚举能力的虚拟化提供者仍不放行。

同一现场窗口的前后对照：v13 返回未知标签数，v14 返回单标签；这是只读能力修复，不是旧窗口实际关闭/重建验收。文件选择、普通目录、窗口身份和完整清单检查保持独立，不能因标签数可读就关闭工作窗口。

接口依据：[Microsoft ItemContainerPattern 文档](https://learn.microsoft.com/en-us/dotnet/api/system.windows.automation.itemcontainerpattern.finditembyproperty)、[.NET WPF 实现](https://github.com/dotnet/wpf/blob/main/src/Microsoft.DotNet.Wpf/src/UIAutomation/UIAutomationClient/System/Windows/Automation/ItemContainerPattern.cs)。空 property 表示枚举所有逻辑项目。

另查到一条启动时序缺口：被排除的系统服务进程创建 Explorer 时，不经过已注入父进程的 CreateProcess 拦截，只能等引擎周期扫描。现场该进程在布局模块初始化时已加载现代界面模块。它支持“注入较晚”的判断，但尚未证明全部开机/导航故障的因果。不能以 Stage3 或 DLL 存在代替首个窗口的布局验收，也不应把系统服务加入全局注入范围来绕过问题。

本轮 native 仍为已安装的 `1.0.9-classicdesk.5`；以下 `.3` 段落是前序修补记录。任务栏热加载错误、实际旧窗口重建和冷启动自动加载尚未验收，不允许发布。

2026-10-16 当前会话测试中，新建 Win10 Ribbon 窗口的标题栏拖动已实际通过；主页／共享／查看和地址栏点击由用户随后手动确认正常。自动化顶部点击曾因工具元素缓存错误中断，不能记为自动化通过。原有 Modern 窗口仍保留，这些结果不覆盖旧窗口迁移、其余导航与窗口控制或增强冷启动。

2026-10-15 在 26H2 私有候选热加载中，一个新建 Ribbon 窗口已实测标题栏拖动、地址栏鼠标点击与导航，以及主页／共享／查看标签展开和收起。原有隐藏 Modern 窗口被系统复用后仍保持旧布局；不能把新窗口测试外推为自动迁移已完成。200 ms 的 WM_NULL 探测仍出现超时，而较长的独立只读探测可收到响应，差异尚在排查；没有放宽结构验收条件。完整冷启动、窗口生命周期及其余顶部操作仍待实测。

## 模块职责与已修的源码问题

`native/explorer-frame-classic.wh.cpp` 保留创建时隔离修复，并移植上游 1.0.9 的经典导航栏重绘修补，候选版本 `1.0.9-classicdesk.3`。此版本尚未实机加载或验收。

- Win10 Ribbon 初始化只注册目标 COM 创建拦截及 `explorerframe.dll` 的 `CNavBar::Load` 经典导航生命周期钩子，不加载 Windows.UI.FileExplorer/FileExplorerExtensions 或现代导航钩子。经典符号解析失败则拒绝初始化，不把缺少修补的半成品计为成功。
- `CNavBar::Load` 前可见、调用后失去 `WS_VISIBLE` 的同一导航对象，补回 `WM_SETREDRAW(TRUE)` 并使其子控件重绘；保留原调用返回值。先前隐藏、COM 查询失败、窗口已更换或销毁时不强制显示。回调不打开/关闭窗口、不移动焦点、不改预加载设置。
- 设置变更保留当前钩子对应的模式，交由引擎重载，不在现有钩子下临时切换全局模式。
- Ribbon 目标创建失败会清空输出指针；不相关 COM 调用透传。
- 导航模式也必须确认延迟加载钩子注册成功；失败返回失败，不能报告为已初始化。
- 导出无用户路径的进程内计数，区分 Init/AfterInit、目标 COM 请求和拒绝次数。`adapterCalls=0` 不能证明 Explorer 打不开，可能是对象复用、其他进程或尚未进入该路径。

模块重载只替换钩子。旧窗口、隐藏预加载窗口和已经选定的 UI 对象不会因此重新创建。当前卸载代码没有对象恢复机制；不要在 DLL 初始化、卸载或 COM 回调里关闭窗口、重启进程或执行阻塞式重建。

`native/Test-ExplorerFrame.ps1` 包含实际模块源码，使用 SDK editing stubs、拦截函数和静态运行库，在不加载引擎、不建立真实钩子、不操作真实窗口的条件下覆盖入口与失败分支。它不证明 Windows 的私有界面兼容性。

## 窗口观察

`ShellExplorerDiagnostics.Capture()` 与 `--inspect-explorer-layout` 是只读入口，不启动引擎，不读取文件夹名称，也不关闭窗口。

观察绑定窗口 PID、线程、会话、进程创建时间和 Explorer 映像，按物理坐标识别顶栏。完整 Ribbon 判据至少包含可见功能区、地址栏、导航、搜索栏和文件内容区域；右侧详情栏的 XAML bridge 不能算作现代顶栏。功能区存在但导航行缺失/隐藏须明确报告异常。最小化、隐藏、枚举不全、无响应或空白窗口不计为布局通过。

2026-10-18 用户截图再次出现 Ribbon 标签存在但地址/搜索/导航整行消失。已核对当时加载的仍为 `.2`，不含上述修补；随后只读采样的展开窗口已具备导航行，不能将稍后快照当作故障瞬间。上游说明该问题与 `CNavBar::Load` 错误恢复重绘、复用预加载窗口有关；当前只确认源码缺口与症状吻合，未证实本次具体调用链。来源：[上游代码](https://raw.githubusercontent.com/ramensoftware/windhawk-mods/main/mods/explorer-frame-classic.wh.cpp)、[WM_SETREDRAW 语义](https://learn.microsoft.com/en-us/windows/win32/gdi/wm-setredraw)。后续实机验收必须加入重复打开/复用、目录切换、最小化恢复、最大化还原、功能区展开收起及每轮地址/搜索/导航可见性与点击验证。

进程身份通过 `ProcessIdToSessionId` 和 `PROCESS_QUERY_LIMITED_INFORMATION` 句柄查询创建时间、映像路径及存活状态，句柄保留到窗口采集结束。实机发现托管 `Process.SessionId` 对存活 Explorer 报退出，后续托管身份查询又被拒绝；不能把这种读取失败当成 Explorer 消失，也不应为读取映像路径要求进程内存读取权限。失败记录只包含阶段、异常类型和 Win32 错误码。

`Complete` 只表示采集完整；`Ribbon` 只表示本次观察到相关结构。`ClicksVerified` 和 `DragVerified` 始终为 false。CLI 退出码 0 也只代表采集完成，不能作为发布验收信号。

响应探测保留 Win32 错误码、实际耗时和本次超时阈值。超时与观察不到响应不是已证明的进程崩溃，也不能因手动操作一次成功就把失败探测覆盖为通过。

## 用户协助的新窗口检查

设置中的“打开并检查新窗口”和显式 `--explorer-check` 入口已接通。窗口构造不执行检查、不启动增强；用户选择本地文件夹后才发送一次打开请求。所有旧窗口均保留，用户核对位置与交互后自行关闭旧窗口。

打开前完整记录现有窗口身份，打开后有界观察新 HWND。原窗口身份改变、清单不完整、复用已有 HWND、多个新候选和超时均不作新窗口确认。即使出现一个新 Ribbon 窗口，也不能据此证明它是所选路径，更不能证明拖动或顶部点击通过。

目录可访问性检查及 Shell 打开请求在独立辅助进程中执行。超过 8 秒仅尝试停止该辅助进程，结果标为未知，不结束 Explorer、不自动重试；已提交的请求仍可能稍后打开窗口。关闭面板只停止观察，不代表打开请求已撤回。

后续窗口观察超时会保留辅助程序的原始结果，避免把“请求是否提交未知”覆盖为只有“没有发现新窗口”的提示。

2026-10-16 修正了发现新 HWND 后过早结束观察的问题：新窗口处于隐藏、最小化、首次响应超时、顶栏尚未创建或混合结构时，在原有 5 秒总观察期内继续观察同一身份，不放宽 200 ms 响应探测。候选 HWND、PID、线程或创建时间改变，以及已观察候选随后消失，均停止归因且保留旧窗口。到期仍未就绪时明确报告未确认。此修正属于检查流程，不是窗口重建执行器；14 项 offscreen 界面测试通过不能代替实机交互验收。

“打开并检查”仍保留旧窗口。新增的“重建旧窗口…”入口会打开独立面板，读取窗口和位置后由用户选定原窗口，并勾选允许在替代窗口确认后关闭原窗口。无选择、无确认、只打开面板都不触发窗口修改。也可显式运行 `--explorer-rebuild`。

## 窗口重建与原生预加载衔接

### 原生预加载兼容设置

系统的窗口预加载会提前创建隐藏 Modern 窗口；晚于它加载的 Ribbon 钩子无法重建已有对象。启用后的打开请求可能复用该窗口。检查入口现在会区分隐藏窗口转为可见与新 HWND，不把它误判为新建成功，也不自动重复打开。Shell 打开请求正常返回但没有进程句柄时属于已提交给现有进程，仍须独立核对窗口和位置；异常或辅助进程超时继续报告未知。

`ExplorerPrelaunch.cs` 提供显式兼容事务。`--explorer-prelaunch inspect` 只读；`prepare-ribbon` 保存当前用户原值后将 Windows 原生 `ShouldPrelaunchFileExplorer` 设为 DWORD 0；`restore` 仅在本工具的已确认记录与当前用户/值相符时恢复原值，包括恢复到原来的不存在状态。已经为 0 的值不取得归属。实际读写前校验本机 Folder Options 的注册定义、HKCU 目标及 0/1/default 语义；不通过 Windows 构建号猜测能力，也不使用仅部分系统版本支持的设备策略。

意图先落盘、回读后确认；异常保留意图且不自动重试。外部修改、切换用户、缺失/损坏恢复记录均阻止恢复。注册表值比较不是操作系统原子 CAS，不能排除外部程序在比较之后并发修改，也无法识别外部程序先改走再改回同值的情况。16 项隔离回归覆盖原值缺失/1/0、写入结果不明、外部修改与记录损坏，不写真实注册表。

兼容准备现接入显式服务当前会话启动及成功暂存 Win10 开机方案后的用户进程步骤。重复准备保留同一恢复记录，不重复改写原值；未提供此原生选项的旧系统无需写入。定义存在但无法识别、外部修改或未完成事务会停止准备。取消管理员提示后，界面说明已经完成的原生准备仍保留，不能声称所有设置均未变化。便携显式 Enable/Resume 也执行同一准备，成功 Restore 后仅恢复本应用拥有且未冲突的原生设置。卸载器的自动恢复尚未接入，现有显式 restore 入口保留；不能宣称全部安装形态迁移完成。

一次性开机准备、完成验收及安装器 EnableNextBoot 均新增只读前置核对：使用安装 OwnerSid 对应的已加载 HKU，而非提权管理员的 HKCU。Win10 方案在系统提供该原生选项时必须为 DWORD 0；不加载离线用户 hive、不从服务账户写设置。`Explorer-StartupPrerequisite.ps1` 与准备/完成脚本一起进入前端构建输出。关闭预加载不消除已有缓存对象，Windows 何时采用新值仍须在同一候选的后续窗口和冷启动中实测。

参考：[Microsoft 的 File Explorer 预加载说明](https://learn.microsoft.com/en-us/windows/client-management/mdm/policy-csp-fileexplorer#disablefileexplorerprelaunch)、[Process.Start 返回值契约](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.process.start?view=net-8.0)。

`WindowsExplorerRebuildHost`、`ExplorerRebuildBroker` 和 `ShellExplorerRebuildPanel` 已在源码接通 `ShellExplorerRebuildCoordinator`。它们尚未执行实机关闭验收，不会随普通应用启动自动重建桌面。

当前适配范围为单标签、本地普通目录、无文件选择、无模态/附属窗口的可响应可见窗口。Shell COM 的位置清单必须与原生窗口清单相符；现代窗口还需 UI Automation 的单标签选择证据，虚拟化/滚动标签容器和多个标签均保留原窗口。经典无标签 Ribbon 窗口要求对应原生子窗口结构。此组合针对本候选做保守识别，不能宣称微软保证了任意 Explorer 版本的完整标签枚举。多标签迁移尚未实现。相关契约参考 [UI Automation Tab](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-supporttabcontroltype)。

其操作契约为：

1. 核对 shell 进程身份、完整窗口清单和明确指定的原窗口修订。只允许可确认的单标签、单位置、无模态操作的普通文件夹；未知标签及虚拟位置不能假定可无损恢复。
2. 先发起一次打开请求，保留原窗口。启动命令返回不代表窗口已出现；已有 HWND 复用、位置不符、身份变化、响应或 Ribbon 未确认，均不能进入关闭步骤。
3. Windows 适配器必须在关闭边界再次核对原窗口、新窗口和 shell 身份/修订；仅关闭明确指定的原窗口。禁止结束共享桌面进程或关闭新窗口。
4. 再次观察原窗口消失且新窗口仍满足结构和位置要求。成功结果是 `RecreatedInteractionUnverified`，不是点击/拖动验收。
5. 同一截止时间和取消令牌覆盖整次操作。超时或结果未知后不自动重新打开、重复关闭。已经交给 Windows 的关闭请求可能无法撤回，适配器必须报告未知结果，不能声称超时等于没有发生操作。

COM/UIA 读取放在独立 STA 辅助进程，使用有大小上限的标准输入输出传递快照，单次辅助程序最多等待 8 秒。目录不写入命令行日志或持久记录。阻塞时只停止辅助程序，保留未知请求结果，不结束 Explorer。关闭前持有原窗口的 COM browser 引用，再次核对原窗口、新窗口和桌面进程的身份、修订和目录；仅调用该对象的 Quit，避免用可能复用的 HWND 向其他窗口投递关闭。发送后有界观察原窗口消失，不重复发出关闭。Windows 没有提供跨窗口状态与关闭的原子事务，因此用户在检查后同时导航仍是需要实机验证的竞态限制。

## 增强会话与进程重建

SessionOnly 服务持有启动时核对的 shell Explorer 进程句柄；该进程退出会结束引擎会话。因此文件夹窗口重建与桌面进程重启必须分开。

`ShellServiceSessionOperations` 现已在启动辅助程序返回后、SCM/原生状态匹配后分别复核 Explorer PID、会话和创建时间，并核对原生 `StartMode`、`SessionId`、`ExplorerPid`。进程被替换、读回失败或任务栏检查失败时返回未确认，不沿用旧会话成功状态。界面保留该详细结果。

2026-10-16 补齐会话入口的身份读取：使用一个 `PROCESS_QUERY_LIMITED_INFORMATION` 句柄查询完整 Windows Explorer 映像、创建时间和退出状态，避免该入口仍依赖曾在受影响主机失败的托管进程元数据查询。完整路径必须匹配 Windows 目录，PID 名称相同不算身份确认。只读实机读取两次一致，并与此前记录的创建时间相符；这不代表服务重新启动或冷启动通过。接口相关的 ServiceSession 13 项与 ServiceUI 12 项隔离回归通过。API 权限依据见 [Microsoft QueryFullProcessImageName](https://learn.microsoft.com/zh-cn/windows/win32/api/winbase/nf-winbase-queryfullprocessimagenamew)。

如果后续证明确实必须重建桌面进程，先处理旧会话结束，再依据新 shell 身份重新检查并启动一次新会话。不能默默修改旧锚点，也不能以 session-only 热启动代替真正的增强冷启动测试。
