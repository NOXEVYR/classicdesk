# ClassicDesk 启动可靠性、Explorer 修复与功能补齐计划

更新：2026-10-15。原始参考产品为 StartAllBack，保留 [逐项对照表](STARTALLBACK_PARITY.md) 的全部稳定 ID。本计划取代旧路线中“先补前端功能、实机后置”的优先次序；不修改历史验收记录。

## 交付目标与当前结论

目标是安装后稳定开机、文件窗口可操作、实际应用保存的外观，并逐步覆盖原参考功能。永久禁用软件、只有预览图、只证明服务运行，均不满足目标。2026-10-25 已完成本机冷启动与旧窗口重建验收，详见 [验收记录](RELIABILITY_ACCEPTANCE.md)。下表和阶段计划保留原排查背景；尚未补齐的 StartAllBack 对照能力及其他系统组合不能宣称全部完成。

用户报告 StartAllBack 在同机没有这些故障，ClassicDesk 使用后多次出现。因此以 ClassicDesk 引入的回归为主线排查，不能在没有证据时归因 Windows 更新。已确认和待确认的问题分开处理：

| 问题 | 已有证据 | 尚缺的闭环 |
| --- | --- | --- |
| 历史开始菜单崩溃 | 原定位模块异常栈；本地加入对象就绪检查 | 不等于此次无崩溃的任务栏缺失也已修复 |
| 开机任务栏缺失 | 原始截图；增强热加载正常；停用增强的重启正常 | 原启动路径下的增强冷启动、同次故障模块耗时与线程栈 |
| 文件窗口 Win10/Win11 混用、顶部失去交互 | 同时存在现代 XAML 顶栏与 Ribbon 窗口；配置仍为 classicRibbonUI；停用 frame 模块后用户确认新窗口可操作、旧窗口仍坏 | 模块创建/卸载/预加载窗口复用的生命周期修复；完整 Win10 布局和顶部交互验收 |
| 功能缺失 | 布局设计未接后端；ClassicStart 未接管系统入口；托盘/Explorer 整组能力缺失 | 按下述阶段逐项实现，不能靠增加预览项结案 |

本地临时停用 frame 模块仅用于恢复文件操作；保存的用户方案保持原样。它不是 Win10 Explorer 完成交付，也不证明开机故障由同一模块造成。

## 第一阶段：故障定位与可靠性修复（发布前置）

1. **保留同次现场**：先记录故障的进程创建身份、模块版本、窗口树、物理像素与 DPI、窗口响应、线程等待和错误事件，再做恢复。记录截图与用户点击/拖动结果；没有崩溃事件不等于没有故障。
2. **补足启动观测**：宿主记录校验、引擎加载、Start、首次 Scan、运行及 End 的有界阶段记录；模块/引擎另记录注入入口、Init/AfterInit、首次桥窗口创建及 Styler TAP 的开始/返回/耗时。宿主日志不能冒充模块初始化证据。故障时记录必须已经可读取，不能等服务退出才写入。
3. **准备一次性增强冷启动诊断**：实现独立于正式兼容验收的诊断许可，绑定指定组件、系统、方案与单次试验；在加载前消费并停用下一次自动重试，保存回退记录。无效/过期/已用/组件变化必须拒绝。不能写假的 EnhancedShellAccepted，不能拿已存在 Explorer 的 session-only 入口代替冷启动。
4. **一次只改变一个主要变量**：先保持原引擎/模块/目标进程和启动语义捕获故障。若现场仍不足，再对比同引擎下六模块全停用，随后按模块组缩小。升级引擎、延迟启动、换模块同时进行的“恢复正常”不能证明某一根因。
5. **具体候选**：核实显式 Include 对 critical 排除的覆盖、父链创建钩子与 APC/远程线程差异；记录 Styler 首次建窗同步 TAP 尝试及跨线程派发。它们目前是可证伪候选，不是已经证实的死锁。最终架构应缩小目标进程范围；是否移除父链注入须与首帧效果一起验证，不能未经验证直接认定为修复。
6. **故障修复验收**：证明修改前后的行为差异；保留原生任务栏/文件操作的可恢复性；对失败、失联、拒绝加载、部分加载分别给出真实状态。上游同步调用若无法取消，明确限制，不用强杀 Explorer 伪装可控超时。

完整的跨启动采集、一次性诊断入口和模块阶段记录准备并经过隔离验证后，才请求下一次整机重启时间。诊断暂不安排自动反复重启。

## Explorer 专项：窗口创建与交互必须一起修

源码候选、观察判据、重建核心与已接通、待实机验收的 Windows 适配器见 [Explorer 生命周期说明](EXPLORER_LIFECYCLE.md)。隔离测试通过不代表本节实机验收完成。

现有 frame 模块通过在创建阶段拒绝 XAML 适配器使窗口使用旧路径。热加载不会把已创建的现代窗口改造成完整 Ribbon；热卸载也不会重建旧窗口。只看 DLL 是否加载，无法确认窗口实际结构和交互。

必须完成以下改造与检查：

- 明确生命周期：首次进程初始化、已有窗口、隐藏预加载窗口、第三方“在文件夹中显示”、新窗口、模块停用与方案切换。不能在存在不兼容窗口时静默宣称全部应用成功。
- 将窗口层结果纳入诊断：标题/拖动区域、地址栏、后退/前进/向上/刷新、工具栏、标签页或 Ribbon、右键、最小化/最大化、DPI 与主题。普通 WM_NULL 通过只代表线程回应。
- 布局采用完整的成功或回退路径；不能留下传统标题栏叠在现代标签页之上、空白大边框或不可交互的半转换状态。旧窗口不能可靠迁移时明确要求关闭并重开指定文件窗口，先保留各标签位置；不强杀共享桌面进程。
- 同时核对新窗口是否复用预加载对象。上游 1.0.9 的 CNavBar 可见状态补丁需要定向验证；不能因版本更新就宣称它能修复现代顶栏点击问题。
- 自动回归使用合成窗口/接口，不点击真实用户文件。真实验收分别覆盖普通打开、双击目录、Win+E、第三方定位文件、重复开关、停止增强后重开；每种入口的创建时机和实际风格可追踪。

## 第二阶段：统一功能与应用状态

### Windows 新增原生能力的适配调整（2026-10-15）

微软 [KB5120998 发布说明](https://support.microsoft.com/en-us/servicing/os/windows-11/2026/08/kb5120998-windows-11-24h2-25h2-update) 已列出原生任务栏四边位置、小任务栏（图标及高度一起缩小）和开始菜单大小/分区设置。它们属于分阶段推出，不能根据 26H2 或 build 数字直接判定某台电脑已启用，也不能把旧的“仅缩小图标”当成新小任务栏。

- 能力目录逐项记录“系统原生可用 / 尚未核实 / 需增强”，保留用户保存的目标外观。先检查本机设置入口和实际效果，再决定实现路径。
- 对位置、标准大小、合并与标签等重叠能力，优先接系统已有实现；一个能力只由一个后端负责，避免系统和注入模块同时修改。自定义像素尺寸、皮肤等超出原生范围的目标仍须单独验证，不能静默丢弃。
- 系统升级后重新核对兼容指纹与功能入口；旧系统的成功记录不得沿用为新系统验收。保留方案和回退记录，界面明确显示当前增强是否未启动、等待验证或运行异常。
- 任务栏新增选项不等于 Win10 Explorer Ribbon 已获原生恢复支持；资源管理器仍需独立完成创建、拖动和顶部点击验收。
- 这些是待实现和待实测的适配要求。本次没有切换实际后端、改系统设置或解除发布门槛。

保留 WPF/.NET 8、皮肤、原方案格式、草稿、修订校验和恢复记录；按责任拆分，不整体推倒重写。

| 层 | 责任 | 禁止混淆 |
| --- | --- | --- |
| 能力目录 | 将稳定功能 ID 映射到适配器、参数、系统支持范围与验收状态 | 参数能保存不代表后端支持 |
| 方案与迁移 | 草稿、已保存、运行方案及设计预览的显式版本/迁移 | 不让 TaskbarDesign 与 ShellProfile 中重复参数各自假装已应用 |
| 激活协调 | 服务/便携入口共用能力检查与启动结果；绑定进程和组件身份 | Running 不等于功能成功 |
| 原生适配器 | 独立启停、窗口就绪、实际结果、撤销与失败边界 | 外壳初始化不能被前端操作任意打断 |
| 兼容记录 | 本次试运行、增强冷启动验收、环境变化后的重新验证 | 原生正常、仅热加载正常不能签发开机兼容 |
| 界面 | 显示未实现、仅预览、可应用、等待窗口重建、已回读、待实机等真实结果 | 用皮肤名或“完整方案”掩盖未实现部分 |

未支持的能力必须明确拒绝应用并保留用户草稿；有外部修改、来源变化、半完成事务时，不覆盖配置或冒领恢复归属。

## 第三阶段：补齐真实效果

下面每组都必须有“设置→真实效果→关闭/恢复”完整证据。对照表内待核实的细节先确认定义，不能删掉或合并成已实现。

| 可用任务栏核心 | T01–T21、A03/A04 | 现有位置/尺寸/高度/背景先验收；接通合并和标签、开始图案、边距与分段；四边停靠需真实后端与工作区管理，不能只映射字段 |

## 跨电脑验收与升级

Q01–Q11 全部保留。发布支持范围须列出实际测试的 Windows build/UBR、外壳文件、架构和组件版本；未测平台不自动获得兼容声明。

- 对声明支持的基础组合，在测试机记录至少 10 次独立启动，其中覆盖重新启动及关闭快速启动后的关机再开；另外验证快速启动恢复、注销/登录、Explorer 重建、睡眠/唤醒。每次都核对从首次可见桌面开始的效果、点击和文件窗口。次数是最低门槛，不是对所有电脑永不出错的保证。
- 覆盖单/多屏、主屏切换、混合 DPI、亮/暗/高对比、鼠键/触摸/无障碍，及其它外壳增强的加载冲突。系统更新或关键组件变化后重新验证；发生异常有受限回退，不能自动不断注入重试。
- 空闲/启动/操作峰值同条件测量，区分前端和共享 Explorer 的资源增加；日志有上限，不永久采集用户文件名、窗口标题或输入内容。
- 干净机器完成源码构建、安装、升级、方案迁移、撤销、卸载和恢复。保留历史版本，不把个人运行目录或缓存复制成通用安装包。

## 发布收口

已获得完成修复后升级上传的授权。上传顺序为：完成本阶段承诺的真实功能和修复 → 冻结源提交 → 构建验收 → 新版本包 → 上传 → 回下载验证 → 更新下载入口。当前未完成的修复候选不能提前作为已解决版本发布。

1. 递增版本；同一个前端旧版本号不能覆盖发布，也不能让更新器拒绝实际新程序。
2. 前端四资产、清单、tag/target_commitish 绑定同一不可变源提交。原生宿主、模块、固定资产清单、编译输入及许可/对应源材料分别闭合。
3. 前端包不能假称包含完整运行组件。完整包需要明确列入运行依赖、来源、许可、NOTICE 和重建方法；缺任何必需输入或分发材料时阻止该交付类型。
4. 执行 [本地发布预检](RELEASE_READINESS.md)；它不代替真实安装、兼容测试或第三方分发材料审查。历史记录保留，不把旧包的摘要改成新包。
5. 对上传资产重新下载，核对大小、SHA-256、ZIP 完整性与单应用根目录；验证 Markdown 目的地和公开下载 URL，保持旧版可恢复。

## 原生尺寸适配候选

`ShellProfile.UseNativeTaskbarSizing` 显式选择由 Windows 管理当前尺寸，默认值省略序列化以保留旧方案和事务指纹。选择原生后，便携激活和服务配置共用的计划生成器不选中 `taskbar-icon-size`；应用面板也不能通过通用尺寸勾选重新启用它。自定义图标、栏高和按钮宽度仍保存在方案中，切回自定义时恢复编辑。该选项不修改系统位置或大小，也不将任意像素参数换算成系统的默认／小尺寸。

Windows 设置入口覆盖系统实际提供的位置、大小、合并按钮和文字标签。是否开放新选项以当前机器的系统设置为准，不仅依据 DisplayVersion；没有新增私有注册表写入。独立开始按钮定位、透明、紧凑托盘和 Explorer Ribbon 仍分别需要验收，不因系统提供原生大小而自动获得兼容声明。

候选已覆盖原生尺寸跨页保存、导入、切回参数、应用选择、生成模块配置和旧 JSON 不变性；真实尺寸变化、模块卸载及冷启动状态仍需候选安装验收。
